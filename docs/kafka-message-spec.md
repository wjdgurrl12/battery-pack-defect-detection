# Kafka 메시지 명세서

배터리 팩 측정 데이터 파이프라인에서 오가는 메시지의 정의다.

| | |
|---|---|
| 문서 버전 | **1.5.0** |
| 최종 수정 | 2026-08-26 |
| 기계 판독용 스키마 | [`kafkadata.json`](../kafkadata.json) (JSON Schema draft 2020-12) |
| 근거 데이터 | `db/data/*.csv` 101개 파일, 479,426행 전수 검사 |

이 문서와 `kafkadata.json` 은 같은 내용이다. **필드를 바꿀 때는 둘 다 고쳐야 한다.**

---

## 1. 파이프라인

```
[Postgres]  →  [sensor generator]  →  [Kafka]  →  [api]  →  [streamlit]
                                    └── 이 문서가 정의하는 구간 ──┘
```

`sensor generator` 가 Postgres 에서 측정 이력을 읽어 Kafka 토픽으로 발행하고, `api` 가 이를 구독한다.
요청/응답이 아니라 **단방향 발행-구독** 이므로, 양쪽이 합의해야 하는 것은 메시지 한 덩어리의 모양뿐이다.

원본 데이터는 2020-08-04 ~ 2021-03-03 에 실제로 수집된 1초 주기 기록이다.
generator 는 이를 재생(replay)하므로 **측정 시각과 발행 시각이 다르다.**

## 2. 토픽 정보

| 항목 | 값 | 비고 |
|---|---|---|
| 토픽 이름 | `battery.pack.measurement` | |
| 파티션 수 | `3` | `KAFKA_NUM_PARTITIONS` 기본값 |
| 메시지 키 | `serial_number` (UTF-8 문자열) | 아래 설명 참고 |
| 메시지 헤더 | `mode` = `chg` / `dchg` | 파티션 배정에는 관여하지 않는다 |
| 값 포맷 | JSON (UTF-8) | |
| 메시지 크기 | 약 2,131 바이트 | 압축 없음, 헤더 포함 |
| 프로듀서 | sensor generator | `acks=all` |
| 컨슈머 | api | `group.id=api-measurement-consumer`, `auto.offset.reset=earliest` |
| 재생 순서 | **충전만**, 팩 오름차순 | 방전은 `EXCLUDE_DCHG` 로 전량 제외(2026-08-26) |
| 발행 주기 | 3초 / 건 (개발용) | 데이터의 측정 간격 5초와는 별개다 |
| 발행 대상 | 38,058건 / 충전 50구간 / 팩 50종 | 3초 간격이면 약 32시간 |
| 발행 조건 | `abs(current) > 1.0` — **통전 구간만** | `database.py` `CURRENT_ON_AMPS`. 아래 8절 참고 |

### 키를 반드시 넣어야 하는 이유

Kafka 는 **같은 키를 항상 같은 파티션**으로 보낸다. 키가 없으면 라운드로빈으로 흩어지고,
파티션 간에는 순서가 보장되지 않는다.

즉 키를 빠뜨리면 **팩 한 대의 시계열이 3개 파티션에 쪼개져 `measured_at` 순서가 깨진다.**
결함 판정은 시간 순서에 의존하므로 여기서 조용히 틀어진다.

**`mode` 를 키에 넣지 않는 이유도 같다.** 키를 `1000_chg` / `1000_dchg` 로 나누면
같은 팩의 충전과 방전이 다른 파티션으로 갈라진다 — 실측으로 6팩 중 4팩이 갈라졌다.
충전이 끝나고 방전이 이어지는 연속된 시계열이므로 순서가 깨지면 안 된다.
그래서 `mode` 는 **헤더**로 붙인다. 헤더는 파티션 배정에 관여하지 않으면서
kafka-ui 목록과 컨슈머가 JSON 을 파싱하지 않고도 구분할 수 있게 해 준다.

## 3. 메시지 구조

최상위는 7개 메타 필드 + 5개 그룹이다.

```
{
  schema_version   메시지 명세 버전
  event_id         메시지 고유 ID
  produced_at      발행 시각
  serial_number    팩 식별자
  measured_at      측정 시각
  mode             충전/방전
  seq              재생 순번

  pack        { voltage, current, power }                   팩 전체 상태
  soc         { rsoc_*, usoc_* }                            충전 상태
  limits      { chg_p_max, dchg_p_max, chg_i_max, ... }     BMS 허용 한계
  cell        { v_min, v_max, dv, voltages[16][11] }        셀 전압 176개
  temperature { t_min, t_max, t_avg, values[16][2] }        온도 32개

  label            결함 라벨 (nullable)
}
```

원본 CSV 는 231개 컬럼이 한 줄에 평평하게 늘어서 있다.
이를 그대로 옮기지 않고 **원본의 논리 구조대로 묶었다**(요약 23 + 셀 176 + 온도 32).

## 4. 메타 필드

| 필드 | 타입 | 필수 | 설명 |
|---|---|:---:|---|
| `schema_version` | string | ✅ | 이 메시지가 따르는 명세 버전. 현재 `"1.2.0"` 고정. 컨슈머는 이 값으로 분기한다 |
| `event_id` | string (UUID) | ✅ | 메시지 고유 ID. Kafka 는 재전송이 있으므로 중복 처리를 막으려면 이 값을 쓴다 |
| `produced_at` | string (ISO 8601, UTC) | ✅ | generator 가 발행한 실제 시각. `measured_at` 과 다르다 |
| `serial_number` | integer | ✅ | 배터리 팩 식별자. **메시지 키와 같은 값** |
| `measured_at` | string (ISO 8601, +09:00) | ✅ | 센서 측정 시각. 원본의 `Date` + `Time` 결합 |
| `mode` | string | ✅ | `"chg"`(충전) 또는 `"dchg"`(방전) |
| `seq` | integer | ✅ | 재생 순번. `(serial_number, mode)` 안에서 0부터 증가. 유실 감지용 |

`mode` 는 **CSV 안에 없고 파일명에만 있다.** 적재 스크립트가 붙여 줘야 하는 값이다.

## 5. 측정 필드

관측 범위는 실제 데이터 479,426행에서 뽑은 최소~최대값이다. 검증에 쓸 수 있지만 물리적 한계는 아니다.

### 5.1 `pack` — 팩 전체 상태

| 필드 | 타입 | 단위 | 원본 컬럼 | 관측 범위 | 설명 |
|---|---|---|---|---|---|
| `voltage` | number | V | `Voltage` | 606.2 ~ 721.5 | 팩 총 전압 |
| `current` | number | A | `Current` | −121.5 ~ 137.2 | **음수 = 충전, 양수 = 방전** |
| `power` | number | kW | `Power` | −78.97 ~ 97.13 | `voltage × current / 1000` 파생값 |

> **⚠️ 원본의 `SOH` 컬럼은 메시지에 싣지 않는다 (v1.2.0).**
> 482,639행 전부 0 인 죽은 컬럼이라 뺐다. DB(`pack_measurement.soh`)에는 원시값이
> 남아 있으므로, BMS 가 값을 채워 주는 날이 오면 명세에 다시 넣으면 된다.

### 5.2 `soc` — 충전 상태

`RSOC` 는 실제 용량 기준, `USOC` 는 사용자 표시용이다.

| 필드 | 타입 | 단위 | 원본 컬럼 | 관측 범위 |
|---|---|---|---|---|
| `rsoc_min` | number | % | `RSOCmin` | 0 ~ 89.86 |
| `rsoc_max` | number | % | `RSOCmax` | 0 ~ 92.00 |
| `rsoc_avg` | number | % | `RSOCavg` | 0 ~ 90.19 |
| `usoc_min` | number | % | `USOCmin` | 0 ~ 100 |
| `usoc_max` | number | % | `USOCmax` | 0 ~ 100 |
| `usoc_avg` | number | % | `USOCavg` | 0 ~ 100 |

하한 `0` 은 결측이 아니라 **만방(완전 방전) 시점에 BMS 가 실제로 내는 값**이다. 그대로 쓴다.

### 5.3 `limits` — BMS 허용 한계

현재 시점에 BMS 가 허용하는 충방전 상한이다. 이상 판정의 기준선으로 쓸 수 있다.

| 필드 | 타입 | 단위 | 원본 컬럼 | 관측 범위 |
|---|---|---|---|---|
| `chg_p_max` | number | kW | `ChgPmax` | 0 ~ 73.59 |
| `dchg_p_max` | number | kW | `DchgPmax` | 0 ~ 144.31 |
| `chg_i_max` | number | A | `ChgImax` | 0 ~ 107.0 |
| `dchg_i_max` | number | A | `DchgImax` | 0 ~ 200.0 |

### 5.4 `cell` — 셀 전압

**`dv` 가 셀 불균형의 1차 지표이며, 결함 판정의 핵심 후보다.**

| 필드 | 타입 | 단위 | 원본 컬럼 | 관측 범위 | 설명 |
|---|---|---|---|---|---|
| `v_min` | number | V | `Vmin` | 3.436 ~ 4.090 | BMS 보고 셀 최저 전압 |
| `v_max` | number | V | `Vmax` | 3.449 ~ 4.110 | BMS 보고 셀 최고 전압 |
| `dv` | number | **mV** | `DV` | 2 ~ 37 | 셀 전압 편차. 클수록 불균형 |
| `voltages` | number[16][11] | V | `M01CV01`~`M16CV11` | 3.435 ~ 4.110 | 176개 셀 전압 전체 |

> **⚠️ `v_min`/`v_max` 는 `voltages` 의 최소/최대와 일치하지 않을 수 있다.**
> BMS 가 별도로 보고하는 값이라 대부분 ±1 mV 이내지만 **최대 64 mV 어긋나는 행**이 있다.
> 셀 편차를 정밀하게 계산해야 한다면 `voltages` 에서 직접 구하라.

### 5.5 `temperature` — 온도

| 필드 | 타입 | 단위 | 원본 컬럼 | 관측 범위 | 설명 |
|---|---|---|---|---|---|
| `t_min` | number | °C | `Tmin` | 24 ~ 40 | 최저 온도 |
| `t_max` | number | °C | `Tmax` | 25 ~ 43 | 최고 온도 |
| `t_avg` | number | °C | `Tavg` | 25 ~ 41 | 평균 온도 |
| `values` | number[16][2] | °C | `M01T01`~`M16T02` | 25 ~ 43 | 32개 센서 온도 전체 |

### 5.6 `label` — 결함 라벨

| 필드 | 타입 | 필수 | 값 |
|---|---|:---:|---|
| `label` | string \| null | ❌ | `"normal"` / `"warning"` / `"defect"` / `null` |

**원본 데이터에 정답 라벨이 없으므로 원본을 그대로 재생한 행은 `null` 이다.**
예외는 도구가 이상치를 심은 행이다 — 그 행의 정답은 심은 쪽이 알므로 `"defect"` 를
싣는다(v1.6.0). 심는 곳은 두 군데다:

- `sensor_generator.py --anomaly-every N` : 재생 중 N행마다 셀 하나를 골라 연속으로 띄운다
- `inject_anomalies.py` : 원하는 팩/셀에 일회성으로 주입한다

컨슈머는 이 값을 판정에 쓰면 안 된다(판정 권한은 api 한 곳뿐이다).
판정 결과와 정답을 맞춰 보는 평가 용도로만 쓴다. `"normal"` / `"warning"` 은
여전히 예약만 되어 있다 — 규칙 기반으로 파생하거나 라벨 데이터를 확보하면 채운다.

## 6. 값 규약

메시지를 다루기 전에 반드시 알아야 하는 4가지다. 전부 실제 데이터로 검증했다.

### ① 전류 부호: 음수가 충전이다

| `mode` | `current` | `power` | 전압 추이 |
|---|---|---|---|
| `chg` (충전) | **음수** | 음수 | 상승 |
| `dchg` (방전) | **양수** | 양수 | 하강 |

일반적인 직관과 반대다. 480,948행 중 위반이 **3행(0.0006%)** 뿐이라 이 규약이 맞다.

부호를 뒤집어 해석하면 충전과 방전이 통째로 바뀌어 **판정 로직 전체가 틀어진다.**

### ② 단위: `power` 는 kW, `dv` 는 mV

`voltage` 가 V, `current` 가 A 인데 `power` 만 kW 다.
`dv` 도 `v_min`/`v_max` 는 V 인데 혼자 mV 다. 섞어 쓰면 1000배 오차가 난다.

### ③ 파생 관계

두 필드는 다른 필드에서 계산된 값이다. 전 행에서 성립을 확인했다.

```
power  =  voltage × current / 1000        (최대 오차 0.078 kW)
dv     =  (v_max - v_min) × 1000          (오차 0)
```

검증에 쓸 수 있고, 필요하면 저장하지 않고 계산해도 된다.

### ④ 시간대: KST 로 간주한다

원본 `Date`/`Time` 에 시간대 정보가 없다. **KST(+09:00)** 로 보고 오프셋을 붙여 발행한다.
`produced_at` 만 UTC 다.

## 7. 배열 인덱싱

팩 하나는 **모듈 16개 × 셀 11개 = 176셀** 이고, 온도 센서는 **모듈당 2개 = 32개** 다.

```
cell.voltages[m][c]      ↔  M{m+1:02d}CV{c+1:02d}      m: 0~15, c: 0~10
temperature.values[m][s] ↔  M{m+1:02d}T{s+1:02d}       m: 0~15, s: 0~1
```

바깥 인덱스가 **모듈**, 안쪽이 **셀 / 센서**다.

```python
# 3번 모듈(M03) 7번 셀(CV07) 전압
v = msg["cell"]["voltages"][2][6]

# 모듈별 평균 전압 — 모듈 단위 이상 탐지의 출발점
per_module = [sum(cells) / len(cells) for cells in msg["cell"]["voltages"]]
```

평평한 176칸 배열이 아니라 2차원으로 둔 이유가 이것이다.
`[2*11+6]` 같은 인덱스 계산이 사라지고, 결함 판정에 필요한 모듈 단위 집계가 그대로 된다.

## 8.5 발행 대상 범위

원본 480,949행이 아래 단계를 거쳐 **38,058건**의 메시지가 된다.

```
480,949행  pack_measurement (원시)
  -1,523행  sentinel(169) / 불완전 행(5) / 1043_dchg(1,349)
479,426행
     ÷ 5    5초 정규화 (1초 파일 72개만 해당, 5초 파일 30개는 그대로)
128,005행
  -2,517행  1043_chg (시간축 파손)
     -방전  EXCLUDE_DCHG - 방전 50구간 전량 (2026-08-26 결정)
 80,313건
     -정지  abs(current) <= 1.0 A 인 행 (CURRENT_ON_AMPS, 2026-08-26 추가)
     -데모  DEMO_SERIALS - 합성 팩 9개 (2026-08-27 추가)
 38,058건  <- Kafka 로 나가는 메시지 (충전만)
```

### 데모 팩 (2026-08-27)

**sensor generator 가 기본으로 재생하는 것은 위 38,058건이 아니라 데모 팩이다.**

원본 50팩은 전부 정상이라 그대로 재생하면 이상 판정이 한 번도 안 나오고, 전량
재생에 32시간이 걸려 발표에서 쓸 수가 없었다. 그래서 원본 팩의 편차 패턴 위에
고장을 주입한 합성 팩 9개(`DEMO01`~`DEMO09`, serial 9001~9009)를 만들었다.

```
  6,009행  DEMO01_chg.csv (팩당)
     -정지  통전 4,077행
     ÷ 5    5초 정규화
    816건  팩당
  7,344건  <- 9팩 합계. 3초 주기로 팩당 41분, 전체 6시간
```

| | |
|---|---|
| 무엇이 심겼는지 | `database.DEMO_PACKS` 에 팩별 유형·자리·크기·기대 판정이 있다 |
| 구성 | 정상 2 · 용접불량 2 · 셀 단위 이상 2 · 센서불량 2 · 검출한계 미만 1 |
| 재생 | `python sensor_generator.py` (기본). 원본 50팩은 `--original` |
| 기본 스트림에서 뺀 이유 | 합성 데이터가 원본 통계에 섞이면 안 되고, 위 38,058건도 흔들린다. `demo=True` 로 부를 때만 나온다 |

`serial` 을 9001~9009 로 잡아 원본(1000~1050)과 겹치지 않게 했다. 덕분에 같은
테이블에 있어도 `serial` 만 보고 갈라낼 수 있다.

### 통전 구간만 발행한다 (2026-08-26)

`abs(current) > 1.0 A` 인 행만 내보낸다. 42,255건(52.6%)이 빠진다.

빠지는 것은 **전부 정확히 `0 A` 인 정지 행**이다 - 전수 검사에서 `0 < abs(current) <= 1.0`
인 행은 한 건도 없었다. 대부분은 충전 완료(SOC 90) 후의 유지 구간이고, 짧게는 충전 시작
직전과 충전 중간의 휴지(0.4~1.4분)다.

| | |
|---|---|
| 왜 빼는가 | 모델의 적용 범위 밖이라 어차피 판정되지 않는다. 발행하면 판정 없는 측정만 쌓인다 |
| 기준값의 출처 | `database.CURRENT_ON_AMPS`. 학습도 같은 상수를 쓴다 — `pack_loader` 가 숫자를 복제하지 않고 `database` 에서 import 한다 |
| **주의 1** | 이 필터는 **세션 경계 신호를 지운다.** 정지가 이어지는 것을 보고 "충전 세션이 끝났다"고 판단할 수 없게 되므로, `api` 가 `measured_at` 공백으로 대신 판단한다(`detector.SESSION_GAP_SECONDS`). 한쪽만 바꾸면 안 된다 |
| **주의 2** (2026-08-27) | **모델에 자체 통전 게이트가 없어졌다.** 예전 행 단위 모델은 비통전 행이 섞여 들어와도 스스로 걸러냈지만, 지금 모델은 여기서 거른 것을 그대로 믿는다. 이 필터를 빼면 판정이 조용히 틀어진다 |

**충전 파일 안에 방전(양수 전류) 구간은 없다.** 전수 검사 결과 `*_chg.csv` 51개 파일의
전류 최댓값은 전부 `0.0` 이다. 충전 중간에 "전류가 갑자기 떨어지는" 것으로 보이는 구간은
방전이 아니라 `0 A` 정지다 (예: `1004_chg` 는 SOC 60.8% 에서 24행(0.4분), `1005_chg` 는
SOC 32.3% 에서 84행(1.4분) 멈췄다가 다시 충전한다).
그 짧은 휴지는 300초 미만이라 **같은 충전 세션으로 이어서 판정한다.**

재생 순서는 **충전 50구간을 전부 보낸 뒤 방전 50구간**이다. 정렬은 `database.py` 의 `ORDER BY mode, serial_number, ...` 한 곳에만 있다.

이 순서에서 `measured_at` 은 단조 증가하지 않는다. 충전 마지막(1050, 2021-03)에서 방전 첫 구간(1000, 2020-08)으로 넘어갈 때 되돌아간다. 팩 하나만 놓고 보면 여전히 충전 → 방전 순이므로 시계열 자체는 온전하다.

### 결측 의심 구간 34개 — 현재 보류

> **2026-08-20 회의:** 충전/방전을 나눠 보내는 방식으로 바꾸면서 아래 34구간의
> 제외를 **보류**했다. 현재는 전부 발행된다. 다시 빼기로 하면 `database.py` 의

## 9. 컨슈머 구현 시 주의사항

**중복 처리.** Kafka 는 at-least-once 라 같은 메시지가 두 번 올 수 있다. `event_id` 로 걸러라.

**순서.** 같은 `serial_number` 안에서만 순서가 보장된다. 서로 다른 팩 사이의 순서는 보장되지 않는다.

**시간 공백.** 원본은 1초 주기지만 **5초를 넘는 공백이 37개 파일에 255건** 있다(최대 3,490초).
시계열을 빈틈없이 연속이라 가정하는 로직은 여기서 깨진다.

**검증.** `schemas.py` 의 Pydantic 모델로 파싱하면 형식 오류가 그 자리에서 잡힌다.
JSON 을 직접 dict 로 다루면 필드명 오타가 런타임까지 살아남는다.

```python
from battery_pack_defect_detection.schemas import PackMeasurement

reading = PackMeasurement.model_validate_json(msg.value)   # 여기서 바로 에러
```
